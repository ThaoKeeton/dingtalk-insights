## Ownership and explicit authority

Core and Runtime stay reusable net8 libraries, with no WinUI or Workbench SDK dependency. The private net10 `DingTalkInsights.Workbench.Bridge` library contains the public-SDK-only coordinator and UI-neutral session/action gate; the plugin adds native controls. Production plugin/bridge never reference host-private Core/App. One session/controller/coordinator belongs to each plugin instance. Page factories create controls only. Page recreation disposes controller and coordinator subscriptions and preserves one shared native action gate; detached queued callbacks are ignored.

Initialize registers exactly one fixed non-sensitive task, `monitor`, with `RequiresPluginStart=true`. The real host commit clears old running/resume intent; generic host Start and resume=true are refused. There is no Start, restore, source/store collection or credential value access during construction, Initialize, factory creation, navigation or configuration load. A confirmed native dialog passes the **same immutable MonitoringPreview** to one session-epoch envelope. The registered delegate claims it once, checks expiry/generation/cancellation and awaits successful context scheduling admission before entering the real controller. The page awaits the actual controller result, rather than treating SDK Running/thread-pool queueing as readiness.

The registered task captures the real original MonitorSupervisor loop after actual success and stays owned through that loop and real controller cleanup. Execution cancellation explicitly calls controller Stop even after Start's linked CTS was disposed. Failed context scheduling/start clears the envelope and intent through the caller/coordinator; the worker never awaits its own SDK Stop. The controller retains its last actual loop task through retirement so a Stop winning the start continuation cannot replace that observation with a placeholder. Natural exit never restarts collection.

Native Stop synchronously invalidates pending previews/controller operations before any SDK persistence/Stop wait, including manual read/analysis/send work with no registered task. Ordinary actions stay serialized. Task-only Stop retains the explicit canonical connection and approved local credential purposes; a later Start needs a fresh preview. Host UserRequest versus plugin Stop/Lifetime/shutdown share idempotent controller/session cleanup without waiting on each other's registered delegate. Dynamic context StopReason upgrades remain terminal. Stop timeout preserves Stopping/error, original loop and lease ownership, and blocks new Start until actual retirement. Coordinator state notifications update the native pending-stop status; pages dispose their subscriptions, and terminal retirement clears them.

Terminal disable/shutdown/initialization failure revokes connections, credential use and recovery, and awaits session persistence, real controller operations, the actual loop and legacy-compatible store lease before completion. No autostart/service, model retry or automatic Webhook is introduced. The shared canonical `state.dpapi` and old `state.dpapi.lock`, budgets, attempts/unknown sends and receipts remain authoritative. No active ledger is copied or reset. Disconnect/terminal cleanup holds the lease through a lower transport that ignores cancellation.

Host secret values use a public-SDK-only async provider. The existing `openai.api-key`, `dingtalk.webhook-url`, `dingtalk.webhook-secret` definitions are joined by `credentials.commit`. Explicit complete save removes that commit first, writes/deletes all three fields, then writes a fresh revision and field hashes last. A missing/malformed/changed commit or mismatching selected field refuses use. Read checks the commit before and after selected values. This is fail-closed batch admission over per-key atomic writes, not a host transaction: interruption can leave some new ciphertext and requires explicit complete re-entry. No secret copying, rollback, fallback or automatic retry occurs. Generic single-field edits invalidate the batch until the plugin explicitly saves it again.

Native choices are host credentials, plugin-local DPAPI or explicitly connected standalone DPAPI (read-only). Unsupported host protection fails safely; choosing another source is explicit. Save/delete revoke old purposes before provider I/O. Separate approval binds provider/revision/owner and selected model/send purposes; previews and actual dispatch validate that binding. Model approval reads no Webhook fields; send approval reads no model field. Values never reach pages, host JSON, reports or diagnostics. Password fields are cleared after save/cancel/unload. Revoke immediately cancels all controller work and joins real operations/registered task retirement while retaining ciphertext and authoritative budget/attempt ledgers. Ignored lower reads/writes/transports remain owned until they actually return. Stop alone retains approved purposes; disable/close/re-enable/restart do not restore them.

## Native functions and packages

The native workspace/settings provide explicit demo open, fixed bounded read preview, continuous monitor preview/start/stop, local/DWS search, source candidates, evidence-validated tentative reports/history, manual evidence resolution, clipboard Markdown and manual send with separate duplicate-risk retry confirmation. Identity/conversation/timezone ranges, DWS path/discovery, polling/retention, model/rates/output/UTC budget/requests and encrypted drafts are explicit settings. Only non-sensitive preferences enter host JSON.

Build with `scripts/build-workbench-plugin.ps1` under SDK **10.0.403**. PackageTool stages private dependencies using the actual new host metadata/deps/framework catalog and WinRT projection graph; the inventory is enforced. The clean plugin contains the plugin/bridge/Runtime/Core private DLLs, deps, manifest and bounded build-info/inventory. SDK/Core-host/App/framework/WinUI/WinRT/EXE/PRI/XAML payloads are excluded. The separate complete native acceptance host carries actual generated main PRI/XAML and a separately labeled test-only control fixture, never a default-context preload of the business plugin DLL. Linux reference compilation uses only a temporary InitializeComponent stub and is never published or executed as native evidence.

The new **Core host** `PluginPackageStore` accepts directory or root-manifest ZIP install, version-increasing update staging, cancellation of untouched Prepared work, removal staging, code-history rollback and startup replay. It is absent from the plugin runtime context. KeepData is unconditional: `StageRemoveAsync` has no keepData argument and there is no purge API. Current plugin data/settings/host secret ciphertext and code history survive removal. Backups contain those three per-plugin trees plus the **whole shared background-tasks.json**. They do not include plugin-state.json or follow the external canonical ledger/DWS profiles; code rollback never restores old business data. Approval and task consent are revoked by successful replay, so even identical code requires fresh trust.

The required order is exclusive UserRoot lease → ApplyPendingAsync → Discover → Restore. Any discovery, including additional roots, permanently seals maintenance for that process; disable, Dispose or a new manager cannot reopen it. Loaded and overlapping paths remain protected until actual process exit. Do not replace or delete loaded DLLs. Unknown/damaged journals retain ownership and fail closed; an unsuccessful replay may truthfully mean verified old code was recovered into place and damaged new bytes quarantined.

The fixed original27154465 presenter includes task/credential/package pages and actual leased startup ApplyPending before any discovery/restore. The source-linked native harness uses those bytes unchanged. Its removal/rollback matrix uses original HostRuntime replay without an apply helper. A nonce-owned helper only installs/stages; separate package recovery tests still exercise guarded apply. The harness has an isolated generated-App bootstrap and is not the unchanged shipping EXE.
