## Runtime and data ownership

Add `DingTalkInsights.Runtime`, a .NET 8 library referencing Core only. It owns the controller, encrypted workspace/credential helpers, and production service boundary. Core remains the one parser, evidence validator, collection engine, supervisor, retention and budget implementation. Extract the existing Windows DPAPI/vault implementation so standalone and future plugin use the same format; no WinUI dependency enters either library. Standalone remains .NET 8 / WindowsAppSDK 2.6.5. Task 2 aligns its native adapter with Workbench .NET 10 / WindowsAppSDK 1.8.260921001, x64.

One controller belongs to a plugin instance. Start, analysis and send use immutable one-use previews bound to the exact request/batch/task/model/payload, current owner/generation/retention/credential revision and a five-minute expiry; dialog-time edits or Stop cannot silently replace approved content. Views only read snapshots, edit its draft, subscribe through disposable subscriptions, and invoke explicit actions. Navigation does not construct controllers, start sessions, restore authority or issue sends. A semaphore serializes manual operations and supervisor ticks. All outer operations register cancellation before any await; Stop and host Lifetime invalidate their generation immediately, then await pending/active work and the supervisor before releasing storage. A source ignoring cancellation cannot commit a late result or save Running. Stop monitoring permits a fresh explicit Start; disconnect releases live ownership and clears raw candidates/results/history; deactivation is terminal and removes subscriptions.

Construction/Initialize perform no disk, credential, process or network I/O. Default state is in-memory demo. An explicit demo-open action uses only `IPluginContext.DataDirectory/demo/state.dpapi`. Workspace drafts/settings save encrypted under the context directory only through explicit load/save actions. Nothing derives LocalAppData or scans old roots.

## Explicit connection and reversible migration

Use one physical canonical `state.dpapi`, selected by the user, rather than copy-and-switch migration. Connection requires an existing state file, an absolute directory with no symbolic-link/reparse-point components, and the same exclusive `state.dpapi.lock` used by shipped v0.2. Acquire it before loading state or touching credentials. An old standalone or second plugin owner makes connection fail closed. Never kill a process, steal a lease or copy a live store. Exclusion is for the explicitly selected canonical store; unrelated roots cannot be represented as mutually excluded.

The connection action explains source/destination (same file), retention/trim, recovery revocation and rollback. Load validates and applies the existing retention policy; no scope, account, model, rates, retention or credential settings are imported automatically. Revoke imported standalone recovery durably before exposing the connection. Corrupt/invalid/expired content confers no authority. Connect does not start collection or read the credential vault. Every Start is explicit and validates the complete request, DWS executable digest/read-only identity readiness, retained next window, and selected credential revision. Plugin authority is volatile and owner-bound; it never calls BackgroundPolicy.Approve or persists an unattended grant. This also prevents an older standalone host inheriting plugin authority.

Rollback: explicitly disconnect/disable, await retirement and release, then launch standalone against that same canonical directory and explicitly review/reconfirm settings/start. Messages, receipts/provenance, contiguous coverage, revisions, unknown model attempts, UTC reservations and returned usage stay in place. No data deletion or stale-budget restoration is required. A separate canonical DPAPI send-attempt sidecar survives even an old v0.2 state JSON rewrite; it is protected by the same state-file lease. The released old v0.2 binary cannot enforce that sidecar for its own sends; returning to it requires manual no-send operation. The maintained standalone source uses the new ledger. Do not promise safe automatic Webhook replay across the old binary.

## Credentials and sends

JSON host Settings are not a vault. `CredentialVault` remains DPAPI encrypted, same-user Windows protection. Credential reuse is a separate concrete action selecting plugin-local credentials or the explicitly connected canonical vault and the allowed purposes (model/Webhook). Selection records only the encrypted-file digest; values are read privately at dispatch and never returned to pages. A revision change invalidates permission. Entering/replacing plugin-local credentials is a separate confirmed action; key creation/provisioning is out of scope. Nothing writes the standalone vault without a separately implemented explicit flow.

Add a bounded hash-only durable Webhook attempt model in Core, persisted in `send-attempts.dpapi` beside canonical state under the same legacy-compatible lease. Hash the approved destination URL and full payload, independent of display-name/signing-secret changes. Save Pending before HTTP; retain Sent, Failed, Unknown and interrupted Pending across Stop, restart, clear and canonical-owner handover. Duplicate page events and concurrent callers are suppressed. A new explicit human-confirmed retry records an incremented attempt before dispatch and warns that duplicates are possible. This is local replay prevention, not server end-to-end exactly-once delivery. No background or demo operation can send a Webhook. Maintained standalone sending shares this boundary.

Errors crossing controller/UI are safe categories. Transport/provider exception bodies, URLs and secrets do not appear in notices, persisted health, workspace documents or reports. Core keeps complete-only contiguous checkpoints, bounded one-hour/two-minute overlap, 40-source increments, retention, read-only=no analyzer, UTC dispatch-day budget, pre-HTTP model attempts, unknown-model suppression and pending-budget defer. There is no model fallback.

## Self-review corrections

The reusable runtime exposed a Core final-report-save issue: after a failed durable save, a newly appended report and usage could remain in memory and become visible or persist on later Stop. A production-boundary RED test now pins rollback of only that undurable report/returned usage, retaining the pre-HTTP attempt and budget reservation. StateStore.cs and its v0.2 serializer/schema remain unchanged, so old-format roundtrip tests exercise that exact production implementation.

Idle snapshots now use a monotonic retention reference; clock rollback cannot resurrect expired visible content. Business snapshots publish while the operation gate is held; editing a draft notifies from a cached snapshot rather than reading mutable engine state.
